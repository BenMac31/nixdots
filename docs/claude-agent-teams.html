01 / Configure once

Your setup

The feature flag lives in your writable user settings. This repo manages it through ai.claude.agentTeams.enable, enabled by default when ai.claude.enable is on. Activation merges the flag without replacing other settings or environment entries.

Your account launcher uses per-account Claude profiles that copy the user settings at launch. Open a fresh interactive claude session to pick up the change. Keep the shared flag in user settings; don’t hand-edit every account profile.

Inspect the flag · terminal
jq -r '.env.CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS' ~/.claude/settings.json
# Expected: 1
claude

Use the default in-process display first. For optional panes, install tmux through Nix, open a tmux session, then run claude --teammate-mode auto. This configuration does not install tmux or change your display preference. Display modes ↗

Your permission setting matters. The account wrapper currently starts Claude in bypassPermissions mode. New teammates inherit the lead’s permission mode. For a session that asks before actions, launch claude --permission-mode default. To change the wrapper’s default, set ai.claude.bypassPermissions = false; and run homeswitch. Permission behavior ↗

02 / Begin with observation

A useful first run

Start with three reviewers and a concrete change. Different review lenses give you independent work without edit collisions. This is a suggested workflow, not a Claude requirement.

Starter prompt · paste into Claude
Create an agent team with exactly three teammates to review the
current uncommitted diff in this repository. Do not edit files.

Name them:
- module-reviewer: check option defaults, imports, and module composition.
- runtime-reviewer: check activation scripts, permissions, and runtime files.
- skeptic: challenge assumptions and look for regressions the others miss.

Give each teammate the relevant repository instructions and task context.
Have them send concrete findings to each other when their work overlaps.
Each finding needs a file and line, consequence, evidence, and confidence.
Use messages to coordinate; use shared tasks if those tools are available.
As lead, wait for all three reports, reconcile disagreements, and return
one prioritized list with suggested verification. Then shut down the team.

For a named change, replace “current uncommitted diff” with a commit range or specific files. This workspace can contain unrelated work, so a narrower scope often produces a better review.

Work shapeSuggested approach
Small fix or a strict sequenceKeep it in one session.
One isolated questionDelegate to a subagent.
Independent investigations that should compare findingsUse a small agent team.
Several workers need the same filesAgree on a design together; assign implementation to one owner.
03 / Write the handoff

Give every teammate a complete brief

Teammates receive project context and their launch instructions, but do not inherit the lead’s chat history. Include the decisions you already made. Context model ↗

  • Outcome: a checkable deliverable, with an explicit stopping point.
  • Ownership: files they may edit, files they may only inspect, and who owns shared interfaces.
  • Constraints: relevant repo rules, compatibility targets, and decisions already settled.
  • Evidence: commands to run and the result to report; distinguish measured facts from hypotheses.
  • Escalation: message the lead before changing scope or editing another owner’s file.

Keep tasks large enough to produce a useful result, but small enough for a review checkpoint. Ask blocked workers to state the dependency rather than start overlapping work. Make the lead responsible for final integration and validation.

04 / Divide by ownership

Parallel edits that remain reviewable

Settle shared interfaces before splitting implementation. Give each teammate a distinct file set; reserve common files such as flake.nix and lockfiles for the lead. Separate Git worktrees help when branches need isolation, but a team does not automatically give each worker one.

Implementation brief · adapt paths first
Create an agent team for [goal] with two implementers and one reviewer.
First propose file ownership and the interface contract; wait for my
approval of that design before assigning edits.

Implementer A owns [file set A]. Implementer B owns [file set B].
The reviewer inspects both changes and reports issues without editing.
Only the lead edits shared integration files or lockfiles.
Include the exact constraints and acceptance checks in each launch brief.
If ownership must change, message the lead before touching the file.

Ask workers for a concise change summary and validation evidence.
As lead, wait for their work, inspect the combined diff, resolve review
findings, and run the final relevant checks. Do not commit or deploy.

Rules to include for this NixOS repo

  • Use one feature enable option, conditional configuration, and parent lib.mkDefault true defaults. Put code beside its closest existing example.
  • Keep secrets in runtime files, outside the world-readable Nix store.
  • Evaluate one output at a time. Don’t evaluate all configurations and don’t run nix fmt.
  • Have the lead coordinate Nix checks and activation. Use nixtest for a requested temporary system trial.

05 / Steer deliberately

Controls, scope, and cost

Three teammates are a sensible starting point. Each has its own context and consumes tokens; add a worker when you have another independent deliverable. Specify a model in the launch brief when you want to control it, for example, “Use Sonnet for the reviewers.”

In-process controlAction
↑ / ↓, then EnterSelect a teammate in the agent panel and open its conversation.
Type in that conversationGive that teammate a narrower task or ask for evidence.
EscClear panel selection; while viewing a teammate, interrupt its current turn.
Ctrl + TToggle the task list where available.
Ask the lead to shut down named teammatesFinish the team after its reports are integrated.

Request a checkpoint after the first finding or design proposal. Stop duplicate investigations early. An idle teammate is not proof that its task passed validation: require the evidence in its handoff. Current controls ↗

For recurring workflows, consider narrowly scoped TaskCompleted or TeammateIdle hooks. A hook exiting with code 2 can return feedback and block completion or idling. Start with manual review before adding automation. Hook behavior ↗

06 / Know the edges

Recovery and disabling

  • No teammates: use an interactive session, explicitly request an agent team, and check for a higher-precedence flag override. Headless claude -p does not spawn teammates.
  • A teammate disappeared: inspect the agent panel or message it by name. Idle rows can hide without the teammate shutting down.
  • After resume: recreate in-process teammates; session resumption does not restore them. Keep findings and remaining work in a durable file.
  • A dependent task is stuck: inspect the deliverable, then ask the lead to correct stale task status.

Only the lead can spawn teammates, and each session has one team. Shutdown may wait for the current call to finish. These are experimental behaviors; check the current limitations when upgrading.

Turn teams off persistently

Set the following in your Home Manager configuration, then run homeswitch. Activation writes the flag as "0".

Home Manager option
ai.claude.agentTeams.enable = false;

For an immediate settings-only change, set the flag to "0" in user settings; the next activation restores the Nix choice. With teams enabled, Claude can also turn named subagent delegations into teammates, even without an explicit team request. Delegation behavior ↗

User settings can be overridden by project, project-local, command-line, and managed settings. Check those sources when the saved user flag and actual behavior disagree. Settings precedence ↗
